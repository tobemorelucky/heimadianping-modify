# Kafka 秒杀秋招面试总结

## 1. 为什么使用 Kafka？

推荐回答：

秒杀流量具有瞬时高峰，不能让每个请求同步占用数据库连接并直接写订单。我保留 Redis Lua 做前置准入，只让库存充足且满足一人一单的请求进入 Kafka。Kafka 将请求入口和数据库订单服务解耦，通过持久化日志承接峰值流量，Consumer 按数据库可承受的速度异步落库，还可以通过 Consumer Group 横向扩容。项目同时需要明确的 offset、失败重试和 DLT，所以正式链路选择 Kafka，并保留 Redis Stream 作为灰度回退。

面试关键词：削峰、解耦、持久化、消费者组扩展、可观测 offset、失败隔离。

## 2. Kafka 解决了什么问题？

Kafka 主要解决四类问题：

1. **流量削峰**：将瞬时请求转成可排队的订单事件，保护 MySQL。
2. **服务解耦**：请求线程只完成准入和消息投递，数据库事务由消费者负责。
3. **可扩展消费**：增加 Consumer 实例即可按分区并行处理。
4. **故障恢复**：未提交 offset 的消息可在服务重启后继续消费，失败消息可进入 Retry/DLT。

Kafka 不直接解决超卖和一人一单。这两项仍分别依靠 Redis Lua 的原子准入、数据库条件更新、业务幂等和唯一索引。

## 3. 为什么 Redis Lua 仍然保留？

推荐回答：

Kafka 适合传输已经通过准入的事件，但不能原子读取并修改 Redis 库存，也不能在入口处低成本判断一人一单。Lua 可以在 Redis 单线程执行模型中一次完成库存检查、用户购买检查、库存预扣和用户标记，避免多个网络往返以及并发条件竞争。这样进入 Kafka 的都是有效请求，减少无意义消息和数据库压力。Kafka 与 Lua 是分工关系：Lua 管准入和原子判断，Kafka 管异步传输和削峰。

## 4. 如何保证消息可靠？

推荐回答：

Producer 使用 `acks=all` 和有限重试，入口会等待最多 10 秒获取 broker 发送结果，只有收到确认才返回受理成功。Consumer 关闭自动提交，数据库事务完成后才手动 ACK。消费失败不 ACK，并转入 Retry Topic；Retry 仍失败再进入 DLT。失败转发器也会等待 broker 确认，转发失败时不提交源 offset。服务重启后，Consumer Group 可以从已提交 offset 之后继续消费。

需要主动说明边界：Redis Lua 与 Kafka 不是同一事务，当前简单实现仍有跨系统非原子窗口。项目没有虚构“绝对不丢”，而是用 broker 确认、重试、日志监控和 DLT降低风险；更高等级要求可继续引入 Outbox 或补偿扫描。

## 5. 如何处理重复消费？

推荐回答：

Kafka 采用至少一次消费，重复消息是正常情况，所以不能依赖“消息只来一次”。项目使用三层幂等：入口 Lua 的用户购买 Set 阻止重复请求；事务服务按 `userId + voucherId` 查询，已存在时直接按幂等成功返回；MySQL 再通过 `(user_id, voucher_id)` 唯一索引处理并发竞态，订单 ID 主键也能阻止同一事件重复插入。事务服务返回后 Consumer 才 ACK，因此重复投递不会生成重复订单，也不会重复扣减数据库库存。

## 6. 如何处理消费失败？

推荐回答：

我把失败分成正常链路、Retry 和 DLT 三个阶段。主 Topic 消费失败后不在原分区无限重试，而是可靠转发到 Retry Topic，避免长期阻塞主分区。Retry Consumer 固定退避 1 秒并额外尝试 1 次；仍失败则转入 DLT。DLT Consumer 记录订单 ID、用户 ID、优惠券 ID、异常原因、时间以及 topic/partition/offset，再由人工判断是否修复数据或重放。任何转发只有收到目标 broker 确认后才允许提交源 offset。

## 7. 为什么不用无限重试？

无限重试会让一条永久错误消息一直占用消费线程，阻塞同分区后续正常订单，并制造大量重复日志和数据库请求。有限重试适合处理短暂抖动，DLT 则给永久失败一个明确终态，使主链路可以继续前进。

## 8. 为什么用 userId 作为 key？

同一个 key 会稳定路由到同一个分区。使用 `userId` 可以保持同一用户事件的分区顺序，同时把不同用户分散到多个分区。若使用热门 `voucherId` 作为 key，同一场活动的全部消息可能集中到单个分区，形成热点并限制消费并行度。

## 9. ACK 为什么必须放在事务之后？

如果先提交 offset 再写数据库，数据库失败后 Kafka 会认为消息已经处理，订单可能永久丢失。当前顺序是参数校验、幂等判断、数据库事务、手动 ACK。事务失败会抛异常且不 ACK，消息进入失败处理链路；事务成功或幂等成功才确认 offset。

## 10. 一分钟项目总结

我把原 Redis Stream 秒杀 Demo 改造成了 Redis Lua + Kafka + MySQL 的异步订单链路。Lua 保证库存和一人一单准入的原子性，Kafka 负责削峰、解耦和故障恢复，Consumer 在本地事务中完成数据库条件扣库存和订单插入，事务完成后手动 ACK。重复消息由业务查询、订单主键和用户优惠券唯一索引保证幂等；失败消息经过有限 Retry 后进入 DLT，避免无限重试阻塞分区。切换使用 `seckill.message.mode`，默认 Kafka，Redis Stream 保留用于灰度回退。完整回归和真实 Kafka 联调都已通过，同时我也明确保留了 Redis 与 Kafka 跨系统非原子窗口这一后续优化点。

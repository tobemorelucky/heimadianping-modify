# Kafka 秒杀架构面试题

## 1. 为什么选择 Kafka？

Kafka 适合秒杀订单异步化的主要原因是：

- 高吞吐与分区并行能力适合突发流量削峰。
- 消息写入磁盘并按副本复制，具备明确的持久化与容灾机制。
- Consumer Group 便于订单服务水平扩展。
- offset 与较长保留期允许故障恢复、重放和追溯。
- Topic 能把入口流量与数据库写入解耦，让数据库按可承受速率消费。

选择 Kafka 不是因为它能自动保证订单只执行一次。端到端仍需要可靠 Producer、手动提交 offset、数据库事务和幂等约束共同完成。

## 2. 为什么不用 Redis Stream？

Redis Stream 能胜任中小规模异步队列，当前项目也已经具备消费组、Pending 和 ACK。但在计划中的生产秒杀场景里，Kafka 更适合作为独立事件总线：

- Kafka 的分区、副本、保留、重放、消费积压治理和跨服务订阅生态更成熟。
- Kafka 的容量主要落在磁盘，适合比 Redis 更长的消息保留和大规模积压。
- Consumer Group、监控和运维工具链更适合后续多个业务消费者接入。
- Redis 可以专注高性能缓存、资格判定和库存预扣，不同时承担核心消息队列与缓存的资源竞争。

这不代表 Redis Stream 本身“不可靠”。迁移是容量、职责隔离和演进需求的选择；若流量较小、团队运维能力有限，保留设计完善的 Redis Stream 可能更简单。

## 3. Kafka 如何保证消息可靠性？

分三段回答：

1. 生产端：`acks=all`、幂等 Producer、有限交付超时与重试；Redis Lua 同时写 Outbox，只有 broker 确认后清理，发送失败可恢复。
2. Broker：Topic 使用 3 副本、`min.insync.replicas=2`，禁止非同步副本强制选主，并监控 ISR 与磁盘。
3. 消费端：关闭自动提交，数据库事务成功后手动提交 offset；写 Retry/DLT 成功后才提交来源 offset。

系统选择至少一次语义，因此会出现重复消息。可靠性的重点是“不静默丢失 + 重复可幂等处理”。

## 4. 如何保证订单不重复？

不能只靠 Redis，也不能只靠 Kafka key。需要数据库最终兜底：

- `orderId` 是订单主键，阻止同一事件重复插入。
- `(user_id, voucher_id)` 是唯一索引，阻止同用户用不同订单号重复购买同券。
- 数据库库存条件扣减与订单插入在同一事务中。
- 重复消费时先识别已存在订单；唯一约束并发冲突使整个事务回滚，不能重复扣库存。

因此即使 MySQL 已提交而 offset 尚未提交，消息重放也只产生一次业务结果。

## 5. 为什么使用 `userId` 作为消息 key？

同一 key 会进入同一分区。使用 `userId` 可以保持同一用户事件有序，并把同一热门优惠券的大量用户请求分散到多个分区。

如果用 `voucherId` 作为 key，最热门的券会形成单分区热点，限制消费吞吐。优惠券总库存不要求消息顺序化，因为 MySQL 使用带 `stock > 0` 的条件更新保证不会超卖。

Kafka key 只影响分区和顺序，不负责幂等。

## 6. 为什么 Kafka 事务不能直接解决全部一致性问题？

Kafka 事务可以原子处理 Kafka 内的读写与 offset，但不能自动把 Redis Lua 和 MySQL 本地事务纳入同一原子边界。系统仍会遇到：

- Redis 预扣成功、Kafka 尚未发送时宕机。
- MySQL 提交成功、Kafka offset 尚未提交时宕机。

前者由 Redis Outbox 补投解决，后者由消费端幂等解决。面试中不应把 `enable.idempotence` 或 Kafka EOS 等同于跨 Redis、Kafka、MySQL 的全链路 exactly-once。

## 7. 如何处理消费失败？

- 对数据库短暂故障等可重试异常，先进行少量、短退避的本地重试。
- 仍失败则转发到分级 Retry Topic，避免长期阻塞主分区。
- 超过总次数后写 DLT，触发告警与人工处置。
- 对非法协议、同订单号不同内容等确定性异常直接进入 DLT。
- 只有 Retry/DLT 获得 broker 确认后才提交来源 offset；转发失败则保留来源消息。

## 8. 如何处理消息积压？

先定位瓶颈，再扩容：

1. 查看 lag、最老消息年龄、消费错误率和 MySQL 事务耗时。
2. 如果是消费者实例不足且数据库有余量，将并发扩展到不超过分区数。
3. 如果分区不足，评估扩分区；注意扩容可能改变 key 的分区映射。
4. 如果数据库已饱和，应先优化 SQL、索引、锁竞争或限流，不能盲目增加消费者。
5. 控制 Retry Topic 的回流速率，避免历史流量二次冲击。
6. 根据订单业务时效决定是否仍可正常创建，过期消息必须走明确的失败/补偿流程。

## 9. 手动提交 offset 仍会重复吗？

会。数据库事务提交成功后，应用可能在提交 offset 前宕机；重启后 Kafka 会再次投递。手动提交解决的是“业务未完成却提前确认”的丢失风险，不负责消除重复。重复由数据库主键、唯一索引和事务处理。

## 10. 如何保证库存不超卖？

- Redis Lua 原子判断并预扣入口库存，快速挡住超额请求。
- MySQL 使用类似 `UPDATE ... SET stock = stock - 1 WHERE voucher_id = ? AND stock > 0` 的条件更新。
- 数据库库存扣减与订单插入在同一事务中。

Redis 是高性能入口防线，MySQL 条件更新是最终防线。两者之间出现长期失败时通过重试、失败记录和受控补偿闭环。

## 11. 服务重启后如何恢复？

- API/Producer 重启后扫描 Redis Outbox，重投没有成功确认的事件。
- Consumer 重启后从组内已提交 offset 继续，未提交记录重新消费。
- 数据库已提交但 offset 未提交的记录会命中幂等规则。
- DLT 与 Retry Topic 持久保留失败上下文，支持受控重放。

## 12. 如何设计压测与故障演练？

压测不仅看接口 QPS，还要观察 Redis Lua 耗时、Kafka Produce P99、Consumer lag、MySQL 事务 P99、锁等待、幂等冲突和 DLT 数量。

故障演练至少覆盖：Lua 后宕机、Produce 超时、broker leader 切换、数据库故障、DB 提交后 Consumer 宕机、Rebalance、Consumer 长时间停止以及积压恢复。验收标准是订单不静默丢失、不重复落库、故障可定位并可恢复。

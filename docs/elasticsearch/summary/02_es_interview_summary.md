# Elasticsearch 商户搜索秋招面试总结

## 1. 为什么使用 Elasticsearch？

### 推荐回答

> 原项目的商户名称搜索使用 MySQL `LIKE '%keyword%'`。数据量增长后，这类前置通配符查询难以有效利用普通 B-Tree 索引，并且无法提供中文分词、相关性评分和灵活的搜索能力。我引入 Elasticsearch 作为商户搜索读模型，用 `match` 查询名称并按 `_score` 排序；MySQL 仍负责事务写入和权威数据，ES 只承担搜索。

### 项目落地点

- `/shop/of/name` 的非空关键词已经切换到 ES。
- 增加独立 `ShopSearchService`，隔离 Controller 与 ES DSL。
- ES 只返回有序店铺 ID。
- MySQL 按主键批量补齐完整 Shop 字段。
- 最终按 ES hits 顺序恢复，避免丢失相关性排序。
- ES 异常时降级到原 MySQL LIKE。

### 不应夸大的地方

- 小数据量、精确查询或简单前缀查询不一定需要 ES。
- 当前只实现名称 match，没有实现多字段、高亮、拼音或复杂打分。
- 当前使用 `standard` analyzer，中文分词仍有优化空间。

## 2. MySQL LIKE 有什么问题？

### 推荐回答

> `LIKE '%关键词%'` 前面带通配符时，普通 B-Tree 索引通常难以直接定位匹配范围，容易扩大扫描量。它做的是字符串包含判断，不会把输入分析成词项，也没有 `_score` 相关性。随着数据和检索需求增长，名称完全命中、部分命中、地址命中等结果无法进行统一、可解释的排序。

### 对比

| 维度 | MySQL LIKE | Elasticsearch match |
| --- | --- | --- |
| 查询方式 | 字符串模式匹配 | 分析后查询倒排索引 |
| 前置 `%` | 普通索引利用困难 | 不依赖 B-Tree 前缀定位 |
| 分词 | 无 | 由 analyzer 决定 |
| 相关性 | 无内置搜索相关性 | `_score` |
| 多字段权重 | 实现复杂 | Query DSL 支持 |
| 事务能力 | 强 | 不作为本项目主事务库 |

### 面试边界

不要回答“MySQL LIKE 一定全表扫描”或“ES 永远比 MySQL 快”。是否走索引、实际扫描范围和性能取决于 SQL、索引、数据分布及执行计划；本项目选择 ES 的主要原因是专业搜索能力和可扩展性。

## 3. 倒排索引是什么？

### 推荐回答

> 倒排索引是从词项反向定位文档的数据结构。文档写入 ES 时，文本经过分析器分成词项，ES 记录每个词项出现在哪些文档中。查询时先分析用户输入，再通过词项直接找到候选文档，而不是逐行做字符串包含比较；同时可以结合词频、文档频率等信息计算相关性得分。

### 示例

```text
文档 5：海底捞火锅
文档 9：北派炭火锅

倒排关系（简化示意）：
火锅 -> [5, 9]
海底捞 -> [5]
北派 -> [9]
```

实际词项取决于 analyzer。索引时和查询时的分析逻辑需要兼容，否则可能出现召回不足或噪声过多。

## 4. 为什么使用 match 而不是 term？

### 推荐回答

> `shop_index.name` 是 `text` 字段。`match` 会先使用字段 analyzer 分析用户关键词，再查询分析后的词项，并计算 `_score`。`term` 不分析输入，更适合 ID、类型 ID、状态或 `.keyword` 这类精确值。对分词后的名称字段直接使用 term，输入可能与索引中的实际词项不一致，容易漏检。

项目中的选择：

- 名称：`match name`。
- 类型 ID：未来可用 `term typeId`。
- 精确名称：未来可用 `name.keyword`。
- 排序：`_score desc`，同分时 `id asc`。

## 5. 为什么 Elasticsearch 不作为主库？

### 推荐回答

> Elasticsearch 的优势是全文检索和聚合，不是替代关系型事务数据库。商户新增、更新和业务约束需要可靠事务与明确的事实来源，所以 MySQL 继续作为主库。ES 是可以从 MySQL 重建的搜索副本，即使索引损坏或 Mapping 升级，也不影响主数据的权威性。

### 主要原因

- MySQL 提供成熟的事务、约束和关系数据能力。
- ES 写入到可搜索通常是近实时语义，不等同于关系数据库事务提交语义。
- 分词器或 Mapping 变化经常需要重建索引。
- ES 副本可以从 MySQL 全量数据和 binlog 恢复。
- 订单、库存等强一致数据不能因搜索改造迁移到 ES。

## 6. ES 和 MySQL 如何保证一致？

### 当前项目的准确回答

> 当前阶段完成了 MySQL 到 `shop_index` 的首次全量同步，文档 `_id` 使用 MySQL 店铺 ID，因此重复同步会覆盖同一文档。实时增量同步尚未实现，所以商户发生新增、更新或删除后，ES 可能暂时陈旧。目前需要重新全量同步恢复一致，下一步计划使用 Canal 订阅 MySQL binlog，实现 ES 的最终一致。

### 完整目标方案

```text
首次上线：MySQL 全量读取 -> Bulk 构建 ES

日常变更：MySQL commit
              ↓
           binlog
              ↓
            Canal
              ↓
     ES upsert / delete by shopId
              ↓
       重试、告警、位点恢复
              ↓
          定期数据对账
```

关键点：

- MySQL 是唯一事实来源。
- 使用 shop ID 作为 ES `_id`，使新增和更新消费具备幂等基础。
- 删除事件必须转换为 ES delete，而不是只处理新增和修改。
- Canal 位点需要持久化，重启后从已确认位置恢复。
- 同步失败需要有限重试、失败记录和告警。
- 定期比较数量、更新时间或抽样内容，发现静默漂移。
- 严重漂移或 Mapping 升级时构建新索引，再通过 alias 切换。
- 这是最终一致，不是 MySQL 与 ES 的分布式强事务。

## 7. ES 返回 ID 后为什么还查 MySQL？

### 推荐回答

> 当前 `ShopDocument` 只保存名称、类型、区域、地址、描述和坐标等搜索字段，而原接口还要返回图片、均价、销量、评分、营业时间等完整信息。为保持接口协议，我让 ES 负责搜索和排序，只返回有序 ID，再用 MySQL 主键批量查询补齐完整 Shop。批量查询结果可能乱序，所以会转成 Map，再按 ES hits 顺序组装。

这种方式的取舍：

- 优点：搜索索引精简，接口字段完整，主数据最新，切换风险低。
- 代价：每次搜索多一次 MySQL 主键批量查询。
- 后续：若搜索 QPS 很高，可扩充 ES 展示字段或结合详情缓存，但需要同时承担更多同步一致性成本。

## 8. ES 宕机如何处理？

### 推荐回答

> 搜索服务捕获 ES 连接、HTTP、JSON 和响应格式异常，记录关键词、页码及堆栈，然后降级到原 MySQL LIKE 分页。这样保证基础可用性，但降级结果不保证 ES 的分词和相关性顺序。生产环境还需要短超时、降级指标、告警和并发保护，避免 ES 故障时大量 LIKE 请求压垮 MySQL。

不能把 ES 异常直接返回为空列表，否则会把系统故障伪装成“没有商户”。

## 9. 一分钟项目陈述

> 黑马点评原来的商户名称搜索直接在 Controller 中执行 `LIKE '%keyword%'`，缺少分词和相关性排序。我先用 Docker 部署 Elasticsearch 8，设计 `shop_index` 和独立 `ShopDocument`，再通过 Bulk API 把 MySQL 的 14 家店铺首次全量同步到 ES。查询侧新增 `ShopSearchService`，非空关键词对名称执行 match 并按 `_score` 排序；ES 返回有序店铺 ID，MySQL 通过主键批量补齐完整字段，最后恢复 ES 顺序并转换为 ShopDTO。ES 异常时降级到原 LIKE。MySQL 始终是主库，当前一致性只做到首次全量同步，后续计划使用 Canal 订阅 binlog，实现增量最终一致和数据对账。

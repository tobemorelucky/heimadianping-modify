# Elasticsearch 商户搜索面试总结

## 1. 为什么不用 MySQL 做商户名称搜索？

可以这样回答：

> MySQL 仍是商户主数据库，但原接口使用 `LIKE '%关键词%'`。数据增长后，这类前置通配符查询很难有效利用普通 B-Tree 索引，而且没有中文分词、相关性评分、多字段权重和搜索高亮。Elasticsearch 更适合承担搜索读模型；MySQL 继续负责事务写入和权威数据保存。

补充要点：

- 小数据量下 MySQL LIKE 简单可用，改造不是因为 MySQL 完全不能搜索。
- 当需求只是精确名称或前缀匹配时，可优先评估 MySQL 索引，不必机械引入 ES。
- 本项目引入 ES 的核心收益是全文检索能力、相关性排序和后续组合搜索扩展。
- ES 故障时可以受控降级到原 LIKE 查询，但降级结果不保证相同相关性。

## 2. ES 倒排索引是什么？

可以这样回答：

> 普通数据库索引通常从文档或行定位字段值；倒排索引则从词项反向定位包含该词项的文档。写入商户名称时，分析器先把文本转换成词项，ES 记录每个词项对应哪些文档。查询时不必逐行做字符串包含判断，而是直接找到相关文档集合，并根据词频、文档频率等信息计算相关性得分。

示例：

```text
文档1：海底捞火锅
文档2：老北京火锅

倒排关系（示意）：
火锅 -> [文档1, 文档2]
海底捞 -> [文档1]
北京 -> [文档2]
```

实际词项取决于索引 Mapping 中配置的分析器。中文搜索不能只写一个 `match` 就结束，还需要保证索引时和查询时的中文分析器设计合理。

## 3. 为什么使用 match，而不是 term？

可以这样回答：

> `shop_index.name` 是 `text` 字段。`match` 会先用字段分析器处理用户输入，再拿分析后的词项查询倒排索引，并产生 `_score`。`term` 不会分析输入，更适合店铺 ID、类型 ID、状态或 `.keyword` 这类精确字段。对分词后的名称字段直接使用 term，容易因为输入和索引词项不完全一致而漏检。

在本项目中：

- 名称搜索：`match name`。
- 类型过滤：`term typeId`。
- 名称完全相等：可使用 `name.keyword`，但它不是本接口的主要全文搜索语义。
- 默认排序：`_score desc`，再用 `id` 做稳定排序。

## 4. ES 和 MySQL 如何保持一致？

可以这样回答：

> MySQL 是唯一权威数据源，ES 是可以重建的搜索副本。一致性采用“全量初始化 + binlog 增量同步 + 重试与对账”的最终一致方案。首次上线从 MySQL 全量构建 `shop_index`；后续由 Canal 订阅 MySQL binlog，把新增、修改和删除同步到 ES。文档 `_id` 使用 MySQL 店铺 ID，使重复事件天然覆盖同一文档。同步失败保留重试和告警，并定期比较数量、更新时间或抽样内容发现漂移。

需要说明的边界：

- 不承诺 MySQL 和 ES 的跨系统强事务。
- 写 MySQL 成功到 ES 可见之间存在短暂延迟。
- 更新事件使用相同 `_id` 执行 index/upsert，删除事件删除对应 `_id`。
- Canal 位点需要持久化，服务重启后从已确认位点恢复。
- 大面积漂移时可以从 MySQL 重新全量构建新索引，再通过 alias 原子切换。

## 5. 为什么 ES 不是主数据库？

可以这样回答：

> 商户数据包含新增、更新、状态管理等业务写入，需要明确的事务约束和稳定的主数据语义，MySQL 更适合作为事实来源。ES 的优势是搜索，不是替代关系型事务数据库。ES 文档更新、refresh 可见性、Mapping 演进和分布式故障模型都与主库不同，因此我们把 ES 定位为可丢弃、可重建的读模型。

具体原因：

- MySQL 提供成熟的事务、约束和关系数据能力。
- ES 通常是近实时可见，不等同于提交后立即可查的主库语义。
- 搜索索引的字段和分析器会演进，常通过重建索引处理。
- ES 数据可以由 MySQL 全量数据和 binlog 恢复，降低搜索系统故障对主数据的影响。
- 订单、库存等强一致业务绝不能因引入商户搜索而迁移到 ES。

## 6. 如何保持接口返回字段和排序？

可以这样回答：

> 当前 ES 文档只保存搜索需要的字段，而原接口返回完整 Shop。为了兼容，我先让 ES 返回按 `_score` 排序的店铺 ID，再通过 MySQL 主键批量查询补齐图片、均价、销量、评分等字段，最后按 ES ID 列表重新排序。MySQL 不再做 LIKE，只做高效主键查询。

为什么需要重新排序：

- `selectBatchIds` 不保证按传入 ID 顺序返回。
- 如果直接返回数据库结果，会丢失 ES 的相关性排序。
- 正确做法是把数据库结果转换为 `Map<id, Shop>`，再按 ES hits 顺序组装。

## 7. ES 不可用时怎么办？

可以这样回答：

> 首期保留受控的 MySQL LIKE 降级，ES 请求设置较短超时，发生连接或超时异常时记录错误和指标，再执行原分页查询。降级必须限并发，避免 ES 故障把搜索流量全部压向 MySQL。不能把异常直接返回为空列表，因为那会把系统故障伪装成业务无结果。

进一步措施：

- 持续监控 ES 延迟、错误率和降级次数。
- 连续失败时可通过简单开关临时固定降级。
- 降级失败返回明确的统一错误响应。
- 首期不为此引入复杂熔断体系，流量增长后再评估。

## 8. 一分钟项目回答

> 原项目的商户名称搜索直接在 Controller 中通过 MyBatis-Plus 执行 `LIKE '%keyword%'`，没有分词和相关性排序。我把搜索职责抽成 `ShopSearchService`，由 Elasticsearch 对 `shop_index.name` 执行 match 查询并按 `_score` 排序。因为当前 ES 文档不是完整展示模型，所以 ES 返回有序店铺 ID，再由 MySQL 主键批量补齐完整 Shop，并按命中顺序恢复。MySQL 仍是主库，ES 通过首次全量同步和后续 Canal binlog 增量同步实现最终一致；ES 故障时受控降级到原 LIKE 查询，同时记录告警并限制降级并发。

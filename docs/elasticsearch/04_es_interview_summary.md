# Elasticsearch 商户搜索面试总结

## 1. 为什么使用 Elasticsearch？

推荐回答：

项目原来的商户名称搜索直接使用 MySQL `LIKE '%keyword%'`。数据量和并发增长后，这种查询难以利用普通 B-Tree 索引，而且不支持中文分词、跨字段召回和相关性排序。Elasticsearch 面向全文检索，能够用倒排索引快速找到包含词项的商户，并对名称、类型、地址和描述设置不同权重，还能扩展类型过滤、评分排序和地理距离查询。因此我把 ES 设计成商户搜索读模型，MySQL 继续做权威数据源。

关键词：全文检索、中文分词、倒排索引、相关性排序、多字段查询、读写分离。

## 2. 为什么不用 MySQL？

推荐回答：

不是 MySQL 完全不能搜索，而是当前需求已经超出简单结构化查询。MySQL 很适合事务、主键查询和精确过滤，但 `LIKE '%词%'` 通常无法使用普通索引，中文搜索只能做字符串包含判断，也没有原生的 BM25 相关性、多字段 boost 和灵活分词能力。商户详情和写操作仍然保留在 MySQL，只有搜索场景交给 ES，这样让两个系统各自处理擅长的问题。

补充说明：如果数据量很小、关键词简单且没有相关性要求，MySQL 仍然足够，不应该为了技术栈而引入 ES。这里引入 ES 的依据是搜索能力和扩展需求，而不是替换数据库。

## 3. 倒排索引是什么？

推荐回答：

传统正排结构是“文档 ID 对应文档内容”，查某个词时需要逐条判断。倒排索引反过来记录“词项对应哪些文档”。例如“火锅”这个词项会关联包含它的商户文档 ID、出现频次和位置。查询时 ES 先通过词典定位词项，再读取对应的倒排列表得到候选文档，最后根据 BM25 等算法计算相关性。

示例：

```text
文档1：海底捞火锅
文档2：北京铜锅涮肉
文档3：重庆火锅店

倒排索引：
火锅 -> [文档1, 文档3]
北京 -> [文档2]
铜锅 -> [文档2]
```

中文不能天然按空格切词，所以需要 analyzer。索引阶段使用分词器生成词项，查询阶段也必须使用兼容的分词规则，否则会出现索引中有词、查询却匹配不到的问题。

## 4. 如何保证 MySQL 和 ES 一致？

推荐回答：

我把 MySQL 定义为唯一事实源，ES 是可重建的搜索副本。一致性分两阶段：首先用可重复执行的全量任务按主键游标分页读取 MySQL，通过 Bulk API 初始化 `shop_index`，并做数量和抽样校验；然后使用 Canal 订阅 MySQL ROW 格式 binlog，把 INSERT、UPDATE、DELETE 转换为以 shop ID 为 `_id` 的 ES upsert 或 delete。重复事件因为 `_id` 固定而保持幂等，失败写入进行有限重试并记录位点，服务重启从持久化位点继续。系统还需要监控同步延迟并定期对账，发现漂移后按 ID 修复或全量重建。

需要主动说明：这是最终一致性，不是 MySQL 和 ES 的强一致分布式事务。搜索可能在短时间内读到旧数据，但不会把 ES 当作权威源。

## 5. 为什么初始化同步和 Canal 要分阶段？

推荐回答：

全量同步先验证 Mapping、中文分词、字段转换和查询效果，同时建立可重建能力。Canal 再解决持续增量问题，它还涉及 binlog 配置、复制账号、位点和故障恢复。如果一次同时上线，搜索问题和 CDC 问题会叠加。分阶段可以分别验收，而且即使实时同步出现严重漂移，也能依赖第一阶段的全量工具恢复索引。

## 6. 如何避免全量同步期间丢增量？

推荐回答：

全量开始前记录 binlog 位点，或者先启动 Canal 暂存增量事件；完成全量快照后，从记录位点回放这段时间的增量，等待同步延迟归零，再做数量和抽样校验，最后切换搜索流量。不能简单地先导一次全量、过几天直接开启 Canal，否则两个阶段之间的修改会永久缺失。

## 7. 为什么 `name` 使用 `text + keyword`？

`text` 用于分词和全文检索，`keyword` 子字段保留完整名称，用于精确匹配、排序或去重。一个字段同时满足两类需求，避免为了精确匹配再复制一份业务字段。地址也可以采用类似设计。

## 8. 为什么 `type` 使用 `keyword`？

店铺类型是有限枚举式标签，例如“美食”“KTV”，主要需求是精确过滤和聚合，所以使用 `keyword`。同时保留数值型 `typeId` 与当前数据库和接口语义兼容。类型名称参与关键词搜索时可以作为精确词项并给予适当权重。

## 9. 经纬度如何存储？

使用 ES `geo_point`。当前数据库 `x` 是经度、`y` 是纬度，因此转换时必须写成 `lat=y, lon=x`。这样后续可以使用 geo distance 过滤和距离排序。经纬度颠倒通常不会在编译时报错，却会导致店铺落在错误位置，所以初始化同步必须包含距离抽样测试。

## 10. ES 挂了怎么办？

搜索服务应设置连接和查询超时并告警。是否降级到 MySQL `LIKE` 取决于流量：小流量可以有限降级，但必须限流，防止 ES 故障把全部搜索流量压回 MySQL；较大流量可以直接返回可识别的搜索暂不可用。ES 恢复后由 Canal 续传增量，若发现数据漂移则执行对账或全量重建。

## 11. 如何处理深分页？

现有接口每页 10 条，浅分页可以先用 `from + size` 保持兼容，但要设置最大页数。因为 ES 需要在各分片收集并排序 `from + size` 条记录，页码越深成本越高。未来无限滚动应使用 `search_after`，并设置稳定排序键，例如 `_score`、业务评分和 ID。

## 12. 一分钟项目回答

项目原来的商户搜索在 Controller 里直接使用 MySQL `LIKE '%keyword%'`，没有中文分词和相关性排序。我设计了 `ShopSearchService -> Elasticsearch shop_index` 的独立搜索链路，外部 `/shop/of/name` 接口保持不变。索引中名称和地址使用 `text + keyword`，类型使用 `keyword`，坐标使用 `geo_point`，评分保留整数；名称在多字段查询中权重最高。数据同步先通过可重建的 Bulk 全量任务完成初始化，再使用 Canal 订阅 MySQL binlog 做增量 upsert/delete，并通过固定文档 ID、失败重试、位点恢复和定期对账实现最终一致。MySQL 仍是权威数据源，Redis 详情缓存、GEO 查询以及已归档的 Kafka 秒杀链路都不受首期改造影响。

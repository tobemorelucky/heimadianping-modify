# AI 运营助手面试总结

## 一、项目介绍

我在 HM-DianPing Plus 中增加了一个独立的商家运营助手。用户可以用自然语言查询店铺基础信息、最近 7 天订单情况和优惠券使用情况。系统由 FastAPI 提供对话接口，通过 LangGraph 编排 DeepSeek 的 Tool Calling；Python 工具只调用 Spring Boot 的 AI 专用只读接口，最终业务数据仍由 Java Service 和 MySQL 提供。

整个方案没有把 LLM 直接接到数据库，也没有引入 RAG、Memory 或多 Agent，重点解决的是结构化实时业务数据的查询与分析。

## 二、为什么不用 RAG？

RAG 更适合从非结构化文档中检索知识，例如制度文档、商家手册或历史运营报告。本项目当前问题是“店铺 1 最近 7 天有多少订单”“优惠券使用率是多少”，答案来自实时、结构化业务表，并且需要执行带明确口径的聚合查询。

如果使用 RAG，需要先把数据库数据转换成文档和向量，还会引入同步延迟、召回误差和额外存储，数值统计也不适合依赖向量相似度。因此当前阶段使用业务 Tool 更直接：LLM 负责判断意图，Spring Boot 负责返回确定的数据。未来若需要回答运营规范或营销知识库问题，可以把 RAG 作为另一类知识工具接入，而不是替代业务查询工具。

## 三、为什么使用 Agent？

用户问题不一定对应固定接口。比如“分析一下店铺 1 最近经营情况”同时需要订单和优惠券数据，普通单轮 LLM 无法自行获取这些实时业务事实。

Agent 的价值是让模型根据语义决定：

1. 是否需要调用工具。
2. 调用哪个或哪些工具。
3. 如何组合工具结果。
4. 信息是否充分，是否需要继续调用。
5. 如何把结构化结果转成自然语言分析。

本项目保留单 Agent 和三个只读 Tool，已经能覆盖当前场景，没有为了技术复杂度引入多 Agent。

## 四、LangGraph 的作用是什么？

LangGraph 将 Agent 的执行过程表示为可控状态图。本项目的核心流程是：

```text
START → Agent → ToolNode → Agent → END
```

当模型返回普通文本时流程结束；当模型返回 `tool_calls` 时，条件路由进入 ToolNode，执行工具后把 ToolMessage 送回 Agent。模型可以一次调用多个工具，也可以在得到结果后继续下一轮工具选择。

相比在业务代码里手写循环，LangGraph 明确了节点、状态和路由，便于测试调用轨迹，并为未来增加审核或超时节点留下扩展位置。本项目没有启用持久化检查点，所以消息状态只存在于单次请求中，不构成 Memory。

## 五、Tool Calling 流程是什么？

以“分析一下店铺 1 最近经营情况”为例：

1. FastAPI 将用户消息传入 LangGraph。
2. Agent Node 把系统指令、用户消息和三个工具定义交给 DeepSeek。
3. DeepSeek 返回订单统计和优惠券统计两个结构化 Tool Call，参数均为 `shop_id=1`。
4. ToolNode 调用对应 Python Tool。
5. Python Tool 通过 HTTP 请求 Spring Boot AI 专用接口。
6. Java Service 和 Mapper 从 MySQL 聚合业务数据。
7. Tool 对返回值实施字段白名单，并生成 ToolMessage。
8. DeepSeek 基于两个真实结果生成最终经营分析。

真实联调中已经捕获到 `get_order_statistics,get_coupon_statistics` 的多工具轨迹，而不只是验证最终文本。

## 六、如何保证 Agent 安全？

安全设计主要采用最小权限和职责隔离：

- 只注册三个明确的只读工具，没有 SQL 执行器或通用 HTTP 工具。
- Agent 不能新增、修改或删除业务数据。
- Python 不持有数据库和中间件凭据。
- Spring Boot 使用专用 AI Controller 控制可访问接口和返回 DTO。
- Python Tool 再次使用字段白名单，避免 Java DTO 扩展时意外暴露字段。
- 店铺 ID 在 Tool 和 Java 服务两侧校验。
- 工具设置 HTTP 超时，并把网络或业务异常显式反馈给 Agent。
- 系统指令要求业务事实必须来自工具，不允许臆造数据。
- LLM API Key 通过 `.env`/环境变量注入，并由 Git 忽略。
- 当前不保存会话 Memory，减少跨用户数据串扰风险。

系统提示词不能单独构成安全边界；真正的安全边界是工具白名单、只读接口、后端校验和凭据隔离。

## 七、为什么 AI 服务不直接访问数据库？

第一，Spring Boot 已经拥有业务模型和统计口径。Python 直连数据库会复制订单状态、时间范围、金额单位等规则，长期容易出现 Java 与 Python 口径不一致。

第二，数据库凭据一旦进入 AI 服务，Agent 的潜在影响面会扩大。通过只读 HTTP 接口，模型只能看到经过 DTO 和字段白名单裁剪的数据。

第三，接口层更容易做鉴权、审计、限流、缓存和版本管理，也能在不改变 Agent 工具协议的情况下调整底层数据库实现。

第四，Java 服务可以继续保证事务和领域约束；AI 服务只负责意图理解与表达，不成为第二套业务系统。

因此最终职责划分是：LLM 决策、LangGraph 编排、Python Tool 适配、Spring Boot 管理业务、MySQL 保存事实。

## 八、项目亮点与后续方向

当前亮点包括真实 DeepSeek Tool Calling、单轮多工具调用、Java/Python 职责隔离、确定性统计口径、字段白名单以及端到端测试。

后续如果继续生产化，可以增加 AI 接口鉴权、调用审计、速率限制、链路追踪、超时预算和结果评测。只有出现文档知识检索场景时再增加 RAG；只有出现跨轮会话需求时再评估 Memory，避免提前引入不必要复杂度。

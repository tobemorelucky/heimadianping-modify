# AI 运营助手面试总结

## 1. 项目中的 AI 助手是什么

AI 运营助手面向商家和平台运营人员，将“过去一周订单趋势如何”“哪张优惠券效果更好”这类自然语言问题转换为受控的只读业务查询。Spring Boot 负责身份、权限和真实数据，FastAPI 承担 Python 服务接入，LangGraph 编排 Tool Calling，LLM 负责理解意图与组织答案。

它不是一个拥有数据库权限的聊天机器人，而是现有业务服务之上的受控分析层。

## 2. 为什么不用 RAG

更准确的回答不是“完全不用 RAG”，而是“首期不以 RAG 为主”。

RAG 擅长从运营手册、活动规则、FAQ 等非结构化文档中检索相关内容，但本项目首期问题主要依赖实时结构化数据，例如订单数、核销率、券库存和店铺排行。这些数据需要权限校验、时间过滤、聚合计算和多个 API 组合，单纯检索文档无法可靠完成。

因此首期使用 Tool-Calling Agent 查询 Spring Boot 提供的只读 API。未来如果增加平台规则和运营知识库，可以把 RAG 封装成 Agent 的第五类只读工具，二者并不冲突。

## 3. 为什么使用 Agent

Agent 的价值不是“能自主做任何事”，而是能在预设边界内完成动态编排：

1. 理解用户的自然语言意图。
2. 选择店铺、订单、优惠券或热门分析工具。
3. 生成符合 Schema 的参数。
4. 根据第一个工具结果判断是否需要第二个工具。
5. 综合结构化结果生成易读结论。

例如“结合订单和优惠券表现，分析本店最近 30 天哪张券更值得继续投放”至少需要优惠券分析和订单统计。固定问答接口会产生大量组合逻辑，而受控 Agent 可以复用少量工具完成组合。

## 4. LangGraph 的作用是什么

LangGraph 用有向状态图管理 Agent 的执行过程。项目可以把流程明确拆为输入检查、意图识别、工具选择、参数校验、工具执行、结果校验和最终回答等节点，并为每条边定义条件。

它解决的主要问题包括：

- 保存本轮问题、授权上下文、工具调用记录和结果等状态。
- 控制多工具调用顺序和条件分支。
- 设置最大步数、最大工具次数和总体超时，避免无限循环。
- 在工具异常时进入有限重试或统一失败节点。
- 让执行路径可观测、可测试、可回放，而不是把全部逻辑放在一段 Prompt 中。

LangGraph 不负责提供业务数据，也不能替代 Spring Boot 的权限和事务逻辑。

## 5. Tool Calling 流程是什么

```text
商家提问
  ↓
Spring Boot 完成认证并注入授权上下文
  ↓
FastAPI 将请求交给 LangGraph
  ↓
LLM 根据工具描述生成结构化 Tool Call
  ↓
LangGraph 校验 Schema、次数和状态
  ↓
Tool Adapter 携带服务凭证调用 Spring Boot 只读 API
  ↓
Spring Boot 再次鉴权并执行确定性查询/聚合
  ↓
结构化 Tool Result 返回 LangGraph
  ↓
LLM 只根据成功结果生成回答
  ↓
输出安全检查、审计并返回用户
```

关键点是 LLM 只提出“调用什么工具、传什么业务参数”，它不直接访问数据库；用户身份、商户 ID 和授权店铺范围由系统注入，不能由模型决定。

## 6. 如何保证 Agent 可靠

### 6.1 数据可靠

- MySQL 仍是权威业务数据源。
- 数量、金额、比例和排行由 Java/SQL 按固定口径计算，LLM 只负责解释。
- 最终答案必须关联本轮成功工具结果，并展示时间范围和统计口径。
- 工具无数据或失败时明确说明，不允许模型补全数字。

### 6.2 执行可靠

- LangGraph 使用确定性节点、条件边和终止节点。
- 设置最大工具调用数、最大循环步数和总超时。
- 网络瞬时错误只做有限重试，持续故障返回可解释错误。
- AI 服务故障与现有核心业务隔离，不影响秒杀、搜索和缓存链路。

### 6.3 权限可靠

- Spring Boot 完成用户认证和每次 Tool API 的对象级授权。
- Agent 只有四个白名单只读工具，不持有数据库和中间件凭据。
- `shopId` 即使通过 Schema 校验，仍必须在 Java 层验证归属。
- 订单明细和个人信息默认不发送给模型，只返回聚合数据。

### 6.4 输出可靠

- Tool 参数使用严格 JSON Schema、枚举、范围和长度限制。
- 输出前检查敏感数据、越权对象和没有证据支持的断言。
- 不把相关性描述成因果关系，不把估算描述成精确事实。
- Prompt、Graph、Tool Schema 和模型版本化，使用固定问题集做回归评测。

## 7. 安全追问回答

### Agent 会不会执行危险操作？

首期不会。工具全部是只读查询，FastAPI 和 LLM 没有数据库凭据，也不提供任意 SQL、任意 URL 或通用代码执行能力。店铺修改、发券、退款、库存调整均不在范围内。

### 如何防止商家查看其他店铺？

不能只依赖 Prompt。Spring Boot 根据登录用户派生商户和授权店铺范围，每次 Tool API 都重新做对象级鉴权；模型传入不属于当前商家的 `shopId` 会直接被拒绝。

### 如何防止 Prompt Injection？

用户输入和数据库文本都按不可信数据处理，不能改变系统规则。工具白名单固定，参数必须通过 Schema 校验，用户文本不会被拼接为 SQL、URL 或鉴权条件，输出还要经过敏感字段和证据检查。

### 为什么还需要 Spring Boot，Python 不能直接查数据库吗？

Spring Boot 已承载领域模型、权限规则、缓存策略和数据库访问。让 Python 直连数据库会复制业务规则、扩大凭据暴露面，并使权限与数据口径分裂。因此 Python 只负责 AI 编排，所有业务查询仍通过 Java 的受控接口完成。

## 8. 一分钟面试回答

我为 HM-DianPing Plus 设计了一个面向商家运营的只读 Agent。用户请求先经过 Spring Boot 认证，再转发给 FastAPI；LangGraph 用状态机控制意图识别、Tool Calling、参数校验、失败处理和最终回答。Agent 有店铺信息、订单统计、优惠券分析和热门数据四个工具，工具实际调用 Spring Boot 的内部只读 API，LLM 和 Python 都不直连数据库。选择 Agent 而不是单纯 RAG，是因为核心数据是实时结构化数据，需要鉴权、聚合和多工具组合；RAG 更适合后续运营规则文档。可靠性上，关键指标由 Java 确定性计算，LangGraph 限制步骤和超时，Java 每次执行对象级鉴权，答案只能基于成功工具结果生成。首期不提供任何写工具，因此不会修改店铺、订单、优惠券或库存。

## 9. 表达边界

- Agent 和 RAG 不是替代关系，应回答“Agent 为主，RAG 可作为知识工具补充”。
- LangGraph 提供编排与状态控制，不自动保证数据正确或权限安全。
- Tool Calling 不是让模型执行 Java 方法，而是让模型生成结构化调用意图，再由受控适配层执行。
- “可靠”不等于 LLM 永不出错，而是通过确定性数据、权限、限制、审计和失败显式化降低风险。
- 当前阶段只有设计，没有实现 FastAPI、LangGraph、LLM 接入或 Java Tool API。

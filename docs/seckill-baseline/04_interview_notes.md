# 秒杀模块面试要点

## 1. 为什么 Lua 成功不等于订单成功？

Lua 只能保证 Redis 内部的库存判断、重复判断、预扣和 XADD 原子。MySQL 是另一个资源，订单最终是否成功取决于 Stream 消费和数据库事务。因此 API 返回的订单 ID表示“已受理”，不是“已落库”。

## 2. Redis Stream ACK 的正确时机是什么？

必须在业务事务提交后 ACK。先 ACK 再写库会在进程崩溃时丢消息；永不 ACK 会造成 Pending 堆积。ACK 的 key、group 和 recordId 必须与实际消费一致，而且要检查返回值。

本项目修复前从 `stream.orders` 读取却 ACK `s1`，属于典型的“命令执行了但确认对象错误”。

## 3. 数据库成功、ACK 失败怎么办？

消息会再次投递，所以消费逻辑必须幂等。再次处理时先查询 `(user_id, voucher_id)`，发现订单已存在就作为幂等成功，然后重新 ACK。数据库唯一索引提供最终并发保护。

## 4. 为什么 `@Transactional` 需要拆到独立 Service？

Spring 声明式事务基于代理。私有方法、同类内部直接调用通常不会经过代理，只在方法上写注解不能保证事务生效。把数据库落库提取为独立 Spring Bean 的公开方法，消费者通过 Bean 调用，事务拦截器才会建立边界。

## 5. 分布式锁能代替数据库事务或唯一索引吗？

不能。

- 锁解决同一时刻的并发执行。
- 事务解决多条数据库语句的原子提交/回滚。
- 唯一索引解决最终数据不变量。

锁可能超时、网络分区或配置错误；业务唯一性必须落到数据库约束。

## 6. 如何防止超卖？

两层防线：

1. Redis Lua 高性能预扣，挡住大部分无资格请求。
2. MySQL 使用 `stock > 0` 的条件更新，受影响行数必须为 1。

数据库扣减和订单插入必须在同一事务中，否则会出现扣了库存但没有订单。

## 7. 如何处理毒消息？

无限重试会阻塞分区/消费者并放大故障。本次采用：

```text
消费异常 → Redis 记录次数 → 500ms 退避 → 最多 3 次
    ↓ 达上限
原子写 stream.orders.failed + ACK 原消息
```

失败 Stream 保留原 recordId、订单信息、次数、异常摘要和时间，便于告警、对账和人工补偿。

## 8. 为什么失败记录和 ACK 要用 Lua？

如果先 ACK 再写失败记录，写失败时消息丢失；如果先写记录再 ACK，进程在中间崩溃会产生重复失败记录。Lua 将两个 Redis 操作放在一次原子执行中，在当前单机 Redis 架构下形成最小可靠闭环。

## 9. Pending List 有什么作用？

消费者组把已投递但未 ACK 的消息放入 Pending Entries List。进程异常后可以继续读取 Pending 重试。多实例环境中，每个消费者名应唯一且稳定；某实例永久下线时，需要 `XAUTOCLAIM/XCLAIM` 把闲置消息转给存活消费者。

## 10. 本次为什么不直接上 Kafka？

引入 Kafka 不能自动修复事务、幂等或错误 ACK。先把 Redis Stream 的确认、事务、唯一约束、重试和失败记录做正确，未来只需替换/桥接消息传输层，数据库消费语义可以复用。

## 11. 下一步 Kafka 改造前需要准备什么？

- 固化订单事件字段：eventId/orderId/userId/voucherId/schemaVersion/occurredAt。
- 保留数据库事务 Service 和唯一索引。
- 明确 Redis Lua 成功与 Kafka 发布之间的可靠桥接，避免双写丢消息。
- Kafka 消费仍按至少一次设计，保留幂等、Retry/DLT 和对账。
- 建立 QPS、拒绝码、Stream/Kafka lag、Pending、失败订单、DB 事务耗时指标。

## 12. 一句话回答

该方案用 Redis Lua 负责高并发资格判断，用 Redis Stream 负责异步削峰，用 MySQL 事务和唯一索引保证最终数据正确，再通过有限重试和失败 Stream 保证异常可追踪；Kafka 只是后续扩展消息能力，不改变这些正确性原则。

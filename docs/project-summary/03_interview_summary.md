# HM-DianPing Plus 项目面试总结

## 1. 三分钟项目介绍

> HM-DianPing Plus 是在黑马点评课程项目基础上完成的一次生产化改造。项目面向本地生活场景，原有功能包括用户登录、店铺查询、优惠券秒杀等，但课程版本在高并发削峰、全文检索和缓存一致性方面仍有明显边界。我的工作重点不是简单增加中间件，而是围绕秒杀、搜索和缓存一致性三条链路完成架构升级，并为每个阶段补充测试、部署文件和开发文档。
>
> 第一条是秒杀链路。入口仍使用 Redis Lua 原子完成库存资格校验和一人一单判断，避免请求直接冲击数据库；Lua 成功后由 Kafka Producer 发送订单事件，Consumer 使用手动 ACK，在消息校验通过并完成数据库事务后才提交 offset。数据库事务内通过条件更新扣减库存并创建订单，同时使用 `(user_id, voucher_id)` 唯一索引作为最终幂等防线。临时消费故障使用有限重试，超过次数后进入 DLT，避免无限重试阻塞分区。Redis Stream 代码暂时保留为配置化回退路径，默认链路已经切换到 Kafka。
>
> 第二条是商户搜索链路。我为店铺建立 `shop_index`，实现 MySQL 全量初始化同步，并把 `/shop/of/name` 从 MySQL LIKE 切换为 Elasticsearch match 查询。ES 负责分词、相关性计算和返回有序店铺 ID，MySQL 再批量查询完整业务数据，最后按照 ES 顺序恢复结果并转换为原有 DTO，所以接口参数和响应结构没有变化。ES 异常时自动降级到原 MySQL LIKE 查询，避免搜索组件故障直接导致接口不可用。
>
> 第三条是缓存一致性链路。我部署 Canal Server 读取 MySQL ROW 格式 binlog，并实现 Spring Boot Canal Consumer，只订阅 `hmdp.tb_shop` 的 INSERT、UPDATE、DELETE 事件。业务侧解析 shop id 后删除 `cache:shop:{id}`，删除成功才 ACK；异常时 rollback 并重试，重复删除则利用 Redis DEL 的幂等性安全处理。这样可以覆盖直接 SQL 或其他应用写库导致的缓存失效遗漏。
>
> 这次改造的主要难点是跨 Redis、Kafka、MySQL 的一致性边界、消息重复与失败处理、ES 排序结果和业务完整数据的组合，以及 Canal 消费确认时机。我采用“入口快速裁决、异步落库、数据库最终兜底”“ES 检索、MySQL 主存储”“binlog 驱动缓存失效”的职责划分解决这些问题。当前完整 Maven 回归基线是 43 个测试、0 失败、0 错误、3 个环境测试跳过；Kafka、ES 和 Canal 的真实环境链路也分别做过独立验证。

## 2. 项目背景

原黑马点评适合演示 Redis 缓存、Lua 和异步下单等基础能力，但要作为可持续开发的项目基线，还需要解决以下问题：

- 秒杀请求与订单落库耦合，高峰流量缺少成熟的异步削峰和失败治理。
- 商户名称使用 MySQL LIKE 查询，缺少分词、相关性排序与面向搜索场景的扩展能力。
- 缓存一致性依赖业务更新代码主动删除，无法覆盖旁路写库和删除失败。
- 阶段变更缺少完整的架构、测试与部署记录，不利于后续 AI 助手扩展和面试复盘。

因此，项目以“不破坏已有协议、保留必要回退路径、控制实现复杂度”为原则，逐步引入 Kafka、Elasticsearch 和 Canal。

## 3. 负责工作

- 加固秒杀数据库事务与幂等约束，设计并实现 Kafka Producer、Consumer、手动 ACK、有限重试和 DLT。
- 设计 `shop_index`、实现店铺全量同步与搜索服务，完成 `/shop/of/name` 的无协议变更切换及 MySQL 降级。
- 部署 Canal 开发环境，实现 binlog 事件消费和店铺详情缓存自动失效。
- 为 Kafka、ES、Canal 建立单元测试、环境门控集成测试、Compose 文件和阶段文档。
- 明确当前架构边界，为后续 AI 运营助手和增量数据同步预留演进方向。

## 4. 技术难点与解决方案

### 4.1 高并发秒杀与订单一致性

**难点：** 请求量可能瞬间超过数据库承载能力；消息可能重复、失败或在服务重启后再次投递；资格校验和数据库事实之间存在异步时间窗口。

**方案：**

- Redis Lua 原子完成库存资格校验、一人一单判断和预扣，入口快速失败。
- Kafka 将流量异步化，按 `userId` 作为消息 key，使同一用户的消息稳定路由到同一分区。
- Consumer 参数校验通过后调用独立事务服务；数据库条件扣库存与订单写入在同一事务中完成。
- 手动 ACK 只发生在业务成功或已识别为幂等重复之后；异常不空提交。
- 唯一索引 `(user_id, voucher_id)` 防止重复订单，有限重试与 DLT 隔离持续失败消息。

**边界：** 当前 Redis Lua 成功与 Kafka 发送并非一个原子事务，极端情况下仍可能出现 Redis 已预扣但消息发送失败，后续可通过发送失败补偿、对账任务或事务消息思路继续加强。

### 4.2 搜索相关性与完整业务数据

**难点：** MySQL LIKE 不提供面向全文检索的分词和相关性排序；如果直接把全部业务字段交给 ES，又会扩大双写和一致性成本。

**方案：**

- ES 使用 match 查询店铺名称，负责检索、评分和排序。
- ES 只返回命中的有序 ID，MySQL 批量补充完整 Shop 数据。
- 使用 ID 到实体的映射按 ES 命中顺序恢复结果，再转换为 `ShopDTO`。
- 空关键词保持原查询逻辑；ES 异常记录日志并降级到 MySQL LIKE。

**边界：** 当前已完成首次全量同步，实时增量同步尚未接入；中文检索使用标准 analyzer，后续可按实际召回效果评估 IK 等分词方案。

### 4.3 数据库更新与缓存失效

**难点：** 在业务代码中“更新数据库后删除缓存”只能覆盖受控写入口，直接 SQL、其他服务写入或 Redis 短暂故障都可能留下旧值。

**方案：**

- Canal 订阅 MySQL ROW binlog，以数据库提交后的变更事实驱动缓存失效。
- Handler 严格过滤 `hmdp.tb_shop`，从 INSERT、UPDATE、DELETE 的行数据中提取 shop id。
- Redis 删除成功才确认 batch；失败 rollback，Client 退避后重连重试。
- 缓存已不存在视为幂等成功，同一 batch 的 shop id 先去重。

**边界：** 当前仅删除店铺详情 Key `cache:shop:{id}`，尚未扩展到 GEO 数据或 ES 增量同步。

## 5. 可量化结果

- 秒杀主链路默认使用 Kafka，Redis Stream 保留为配置化回退。
- `/shop/of/name` 已使用 ES match 检索，并保持原接口协议和异常降级能力。
- `tb_shop` 的三类行变更可自动触发店铺详情缓存删除。
- 最新完整回归：43 个测试，0 失败，0 错误，3 个环境测试跳过，`BUILD SUCCESS`。
- Kafka、Elasticsearch、Canal 的本地真实链路均有独立测试与操作文档。

## 6. 三十秒精简版

HM-DianPing Plus 是我在黑马点评基础上做的生产化升级。我保留 Redis Lua 作为秒杀入口的原子资格校验，用 Kafka 完成异步削峰，Consumer 通过事务、唯一索引、手动 ACK、有限重试和 DLT 保证订单可靠落库；商户搜索改为 ES match 检索，再由 MySQL 补齐完整数据并提供异常降级；缓存一致性则通过 Canal 监听 `tb_shop` binlog，成功删除 Redis 店铺缓存后才 ACK。整个改造保持既有接口不变，并通过完整回归和真实中间件集成测试建立了稳定基线。

## 7. 面试表达注意事项

- 不把“最终一致”表述成“强一致”；明确 Redis、Kafka、MySQL 之间仍有异步窗口。
- 不声称 ES 已实时同步；当前只有全量初始化，增量同步是后续工作。
- 不声称 Canal 更新缓存；当前策略是删除缓存，由下一次读请求回填。
- 不声称 Redis Stream 已删除；它仍是可配置回退链路，默认模式为 Kafka。
- 先讲业务问题和职责划分，再讲中间件名称，避免堆砌技术栈。
